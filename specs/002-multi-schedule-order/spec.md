# Feature Specification: 多车次合并下单与优惠券支持

**Feature Branch**: `002-multi-schedule-order`
**Created**: 2026-05-13
**Status**: Draft
**Input**: User description: "当前购票功能支持多个车次(schedule_ids)提交订单。涉及功能：1. 查找可用优惠券支持多个车次，每个车次选择一张优惠券。2. 验证优惠券支持多个车次。3. 创建订单支持提交多个车次和多张优惠券。"

## Clarifications

### Session 2026-05-13

- Q: 当一张优惠券对多个车次都可用、需要在它们之间二选一时，采用哪种分配策略？ → A: **Earliest-date-first**（按车次出发日期升序贪心分配，较早出发的车次优先选取并消费可用券；较晚的车次只能从未被消费的券中选，必要时退化为"无券"。简单确定，可能令较晚车次失去其唯一可用券——接受的权衡。）

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 同一监控轮次内多个可购车次合并为一个订单 (Priority: P1)

监控发现一个 cycle 内有 N 个目标日期都已出票（N ≥ 1），用户希望系统将这 N 个车次合并提交为**一个订单**，而不是逐次创建 N 个独立订单。这避免了多次结算、多次支付、多次通知的割裂体验，也减少了对外部 API 的调用压力。

**Why this priority**: 这是本特性的核心交付物。当前一轮监控对每个车次单独下单（OrderService.tryCreateOrder 仅接受单个 ScheduleItem），上游约束导致用户在小程序内要分别完成多笔支付，体验差且容易遗漏。

**Independent Test**: 模拟一次监控轮次返回两个不同日期且都有票的车次，验证：(1) 仅创建一个订单；(2) 订单包含两个 schedule_id；(3) 成功通知包含两个日期。

**Acceptance Scenarios**:

1. **Given** 监控目标日期 [D1, D2]，且当前 API 返回这两天都有余票，**When** 监控 cycle 执行下单流程，**Then** 系统恰好创建 1 个订单，该订单包含 schedule_id_1 与 schedule_id_2。
2. **Given** 监控目标日期 [D1, D2, D3]，仅 D1 与 D3 有余票（D2 无票），**When** 监控 cycle 执行下单流程，**Then** 系统创建 1 个订单，包含 schedule_id_1 与 schedule_id_3，D2 等待下一轮。
3. **Given** 监控目标日期 [D1, D2]，但 D1 已有"已支付"订单，**When** 监控 cycle 执行下单流程，**Then** 系统仅就 D2 创建订单，不重复购买 D1。
4. **Given** 监控目标日期仅 [D1] 一天且有余票，**When** 监控 cycle 执行，**Then** 系统创建 1 个仅含 schedule_id_1 的订单（保持单车次场景行为不变）。

---

### User Story 2 — 每个车次独立选取最适用的优惠券 (Priority: P2)

合并下单时，用户希望系统对每个车次独立挑选并应用一张可用的优惠券。一张优惠券只能用于一个车次（同订单内不可复用），且其余未被选中的优惠券应保留以备后续使用。

**Why this priority**: 优惠券是用户真实感知的"省钱"价值；若合并下单时丢失了原本可用的折扣，特性就成了倒退。

**Independent Test**: 给定两个车次和两张分别只对各自车次"可用"的优惠券，验证下单请求中 `coupon_ids` 对每个车次都映射到正确的优惠券。

**Acceptance Scenarios**:

1. **Given** schedule_id_1 与 schedule_id_2，账户中有两张优惠券 C1 (仅对 1 可用) 与 C2 (仅对 2 可用)，**When** 系统执行合并下单，**Then** 订单的 coupon_ids 包含 {schedule_1 → C1, schedule_2 → C2}。
2. **Given** 同一张优惠券 C 对 schedule_1（出发日期较早）与 schedule_2（出发日期较晚）均标记为"可用"，且账户中仅此一张，**When** 系统执行合并下单，**Then** 系统将 C 应用于 schedule_1（按出发日期升序优先分配），schedule_2 不应用优惠券。
3. **Given** schedule_1（较早）有 3 张可用优惠券（其中包含券 X），schedule_2（较晚）仅有 1 张可用优惠券且恰好是券 X，**When** 系统执行合并下单且 schedule_1 经价格验证后选定的第一张券正是 X，**Then** schedule_1 应用券 X，schedule_2 因唯一候选已被消费而按"无券"处理，订单仍成功创建。

---

### User Story 3 — 部分车次无可用优惠券时仍能成功下单 (Priority: P3)

合并下单不应因为某个车次没有可用优惠券而整体失败。系统应允许"有的车次带券、有的车次不带券"的混合订单，让用户至少完成订票。

**Why this priority**: 优雅降级。订票成功是首要诉求，优惠券是附加价值；现有单车次行为就是"无券也下单"，多车次必须保持一致。

**Independent Test**: 给定两个车次，仅其中一个有可用优惠券，验证下单仍成功且 coupon_ids 仅包含有券车次的映射。

**Acceptance Scenarios**:

1. **Given** schedule_1 有可用优惠券 C1、schedule_2 无任何可用优惠券，**When** 系统执行合并下单，**Then** 订单成功创建，coupon_ids 仅含 {schedule_1 → C1}。
2. **Given** schedule_1 与 schedule_2 均无可用优惠券，**When** 系统执行合并下单，**Then** 订单仍成功创建，coupon_ids 为空。
3. **Given** schedule_1 有 5 张候选优惠券但全部通过价格验证失败、schedule_2 有可用优惠券 C2，**When** 系统执行合并下单，**Then** 订单成功创建，coupon_ids 仅含 {schedule_2 → C2}。

---

### Edge Cases

- **空车次列表**：合并下单 API 收到空 `schedule_ids` 时，MUST 直接拒绝（业务异常），不发出任何下单请求。
- **重复车次**：`schedule_ids` 中出现重复值时，MUST 在提交前去重；不得对外发出含重复 schedule_id 的请求。
- **车次已发车**：在合并下单前 MUST 排除发车时间早于当前时间的车次；若过滤后列表为空则不下单。
- **存在待支付订单**：任一目标日期已有"待支付"订单时，MUST 抛出 `UnpaidOrderException`、停止监控、写入告警日志，不发起合并下单（沿用现有单车次行为）。
- **混合已支付/未购日期**：已存在"已支付"订单的日期 MUST 从本次合并下单中剔除；剩余日期若仍 ≥ 1 则继续合并下单，剩余为 0 则跳过。
- **车次跨日**：若一次合并下单的车次涵盖不同日期，订单成功通知 MUST 在文案中列出全部日期，不得仅显示其中一个。
- **优惠券价格验证全部失败**：某车次所有候选券验证失败时，该车次按"无券"处理，整体订单仍然下单（见 US3）。
- **一张优惠券标记可用于多个车次**：同订单内 MUST NOT 将同一张优惠券分配给两个车次（避免重复消费）；按**车次出发日期升序**分配，较早出发的车次优先消费可用券，较晚车次必要时按"无券"处理。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在一次合并下单中接受 1 到 N 个 `schedule_id`（N 由 API 上限决定，不在本特性中限制），并将其作为单个订单提交至外部下单接口。
- **FR-002**: 系统 MUST 支持查询"对某个 `schedule_id` 集合可用"的优惠券集合；返回结果按车次组织（每个车次得到自己的可用券列表）。
- **FR-003**: 系统 MUST 对每个 `schedule_id` 独立选择**至多一张**优惠券；同一订单内同一张优惠券 MUST NOT 被分配给两个不同车次。当存在跨车次可用券冲突时，MUST 按**车次出发日期升序**处理：较早出发的车次优先选取并消费可用券，较晚的车次仅能从尚未被消费的券中选取，否则该车次按"无券"处理。
- **FR-004**: 系统 MUST 通过价格验证接口确认所选 (schedule_id, coupon_id) 组合的有效性。验证失败的优惠券 MUST 被丢弃，该车次回退到尝试下一张候选券或最终"无券"。
- **FR-005**: 系统 MUST 在合并下单请求中按外部 API 约定结构提交 coupon 映射：`{scheduleIdStr → {categoryIdStr → couponId}}`，仅包含被验证通过的优惠券。
- **FR-006**: 系统 MUST 在合并下单成功后产生**一条**购票成功记录与**一条**外部 webhook 通知，文案 MUST 列出本次订单包含的全部日期。
- **FR-007**: 系统 MUST 在合并下单前剔除：(a) 发车时间已过的车次；(b) 已有"已支付"订单的日期对应的车次。
- **FR-008**: 系统 MUST 在发现"待支付"订单时（任一目标日期）保持现行行为：抛出 `UnpaidOrderException`，停止监控，写入待支付告警日志，**不**发起合并下单。
- **FR-009**: 系统 MUST 在 `schedule_ids` 列表为空或过滤后为空时跳过本轮下单（不抛错，等待下一轮监控）。
- **FR-010**: 合并下单单车次（N=1）的行为 MUST 与既有单车次下单完全等价，不引入回归。
- **FR-011**: 系统 MUST 记录每次合并下单尝试的 schedule_id 集合与最终应用的 coupon 映射，便于事后审计与排错。

### Key Entities

- **ScheduleSelection（车次选集）**：一次合并下单所针对的车次集合，包含 N 个 `schedule_id`、对应的发车日期与发车时间；用于过滤、去重、跨日校验。
- **CouponAssignment（优惠券分配）**：从 `schedule_id` 到一张已通过价格验证的 `CouponItem` 的映射；同一张 CouponItem MUST 在一个 CouponAssignment 内最多出现一次。
- **MultiScheduleOrder（多车次订单）**：合并下单请求与响应的领域抽象，包含 ScheduleSelection、CouponAssignment、上下车站点 ID 与路线 ID；落地为一次外部下单调用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 当一轮监控发现 N 个有票目标车次（N ≥ 2）时，调用外部下单接口的次数 MUST 等于 1（而非 N）。
- **SC-002**: 当 N 个车次中有 K 个车次存在可用优惠券（0 ≤ K ≤ N），最终下单请求的 `coupon_ids` 映射条目数 MUST 等于"经过验证可用且未被重复分配"的优惠券数；该数值 MUST ≤ K，且 ≤ N。
- **SC-003**: 在外部小程序中查看本次下单产生的订单数量，N 个目标车次合并下单后 MUST 仅显示 1 个待支付订单（而非 N 个）。
- **SC-004**: 当 N=1 的单车次场景下，本特性引入后的下单成功率、通知文案、日志记录与既有单车次行为的差异 MUST 为零。
- **SC-005**: 当账户内某张优惠券对 ≥ 2 个车次标记可用时，订单提交后该券的实际消费次数 MUST 为 1。

## Assumptions

- **优惠券一次性使用**：单张优惠券在一个订单内最多被分配给一个车次。这是优惠券类系统的行业通行语义，外部 API 未声明允许跨车次复用。
- **优惠券验证策略保持现状**：对每个车次按可用列表顺序逐张尝试价格验证，第一张通过即采用；不为了"最大折扣"而做组合搜索。本特性的目标是支持多车次合并下单，而非优化折扣策略。
- **车次顺序按日期升序（Earliest-date-first）**：当存在"同一张券对多个车次都可用"的冲突时，按车次出发日期升序贪心分配——较早出发的车次先遍历其可用券列表、按顺序通过价格验证后即消费该券；较晚的车次仅能从尚未被消费的券中选取。这是 Clarifications #1 的最终决定，优先保证确定性与实现简单性，接受"较晚车次可能失去其唯一可用券"的权衡。
- **批量验证退化为逐次验证**：外部价格验证接口虽然结构上支持一次传入多车次多优惠券，但为了与现有"逐张试错"语义一致，本特性默认采用 per-(schedule, coupon) 的验证调用；后续若发现 API 调用量成为瓶颈再优化为一次性批量验证。
- **目标日期来自现行监控配置**：本特性不引入新的"用户主动选取多个 schedule_id 下单"的对外入口，仅扩展监控 cycle 自动合并下单与底层 OrderService 的多车次能力。任何新的对外入口（如 HTTP endpoint）将由后续特性单独定义。
- **重试与失败处理**：若合并下单请求失败（5xx 或网络异常），保持现行行为——记录错误日志、等待下一轮监控自动重试；不为多车次场景引入额外的部分重试/分裂下单逻辑。
